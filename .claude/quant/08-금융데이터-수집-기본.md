> 정리일: 2026-05-20

## 1. 글의 핵심

이 장은 국내 주식 퀀트 분석에 필요한 기본 데이터, 즉 종목코드, 시장구분, 업종, 시가총액, PER/PBR/EPS/BPS/배당수익률 같은 개별종목 지표, WICS 섹터 구성종목을 무료로 수집하고 정리하는 방법을 설명한다.

Market Pulse의 `MP_CORE` 관점에서는 다음이 중요하다.

- 종목 universe는 가격 데이터만으로 만들면 부족하고, 시장구분, 업종, 시가총액, 특수종목 제외 규칙이 필요하다.
- KRX 데이터는 업종분류 현황과 개별종목 지표를 결합해야 모델 입력으로 쓸 수 있다.
- 최근 영업일 자동 결정, 인코딩, 중복 컬럼 처리, 교집합 merge, 스팩/우선주 제외 같은 클렌징 규칙이 필수다.
- WICS 섹터 정보는 섹터 중립, 섹터 분산, 섹터 모멘텀 피처에 사용할 수 있다.

| 데이터 | 원문 수집 방식 | 주요 필드 | MP_CORE 활용 |
|---|---|---|---|
| KRX 업종분류 현황 | KRX 정보데이터시스템 CSV 다운로드 요청 | 종목코드, 종목명, 시장구분, 업종명, 종가, 등락률, 시가총액 | stock universe, market/sector, market cap filter |

| 최근 영업일 | 네이버 금융 증시자금동향에서 날짜 추출 | YYYYMMDD | 최신 기준 데이터 자동 수집 |
| WICS 섹터정보 | WiseIndex JSON API | 섹터코드, 섹터명, 구성종목, 비중 | sector factor, sector neutral portfolio |

## 3. KRX 데이터 수집 구조

원문은 KRX 정보데이터시스템의 엑셀/CSV 다운로드 과정을 개발자 도구로 분석한다. 흐름은 아래와 같다.

```text
1. GenerateOTP endpoint에 조회 조건 POST
2. OTP 코드 수신
3. download_csv endpoint에 OTP와 referer header를 함께 POST
4. EUC-KR CSV 텍스트 수신
5. CSV parsing
```

핵심 주의사항:

- KRX 다운로드는 단순 GET이 아니라 OTP 발급 후 다운로드하는 2단계 구조다.
- OTP를 바로 제출하면 서버가 로봇으로 볼 수 있으므로 referer header가 필요하다.
- 한글 데이터는 EUC-KR 인코딩 처리가 필요하다.
- KOSPI와 KOSDAQ은 시장코드를 바꿔 각각 받은 뒤 합친다.

### Market Pulse 적용

현재 프로젝트는 과거의 KRX 웹 다운로드 방식보다 안정적인 KRX Open API를 이미 사용하고 있다.

따라서 이 문서의 코드를 그대로 가져오기보다는 아래 개념을 반영한다.

- KRX 응답 필드와 DB 필드의 명시적 매핑
- KOSPI/KOSDAQ/ETF/기타 시장 구분
- 시가총액 기준 정렬
- 스팩, 우선주, 펀드, 해외상장 특수종목 제외 규칙
- 최근 영업일 또는 지정 기준일 기반 수집
- 원천 데이터와 정제 데이터 분리

## 4. 업종분류 현황 데이터

원문의 KRX 업종분류 현황 데이터는 다음 필드를 가진다.

| 필드 | 의미 | MP_CORE DB 후보 |
|---|---|---|
| 종목코드 | 주식 코드 | `asset_code`, `stock_master.code` |
| 종목명 | 종목명 | `asset_name`, `stock_master.name` |
| 시장구분 | KOSPI/KOSDAQ | `market`, `asset_type` |
| 업종명 | KRX 업종 | `sector` |
| 종가 | 기준일 종가 | `close_price` |
| 등락률 | 전일 대비 등락률 | daily return 검증 보조 |
| 시가총액 | 기준일 시가총액 | `market_cap`, universe filter |

### MP_CORE 활용

- `market_cap_rank`: 시가총액 순위 피처
- `liquidity_universe`: 시가총액/거래대금 기준 후보군
- `sector`: 섹터별 과집중 방지, 섹터 모멘텀, 섹터 중립화
- `market`: KOSPI/KOSDAQ 구분별 benchmark와 상대수익률 계산

## 5. 개별종목 지표 데이터

원문의 개별종목 지표 데이터는 가치 팩터의 출발점이다.

| 필드 | 의미 | 모델 활용 |
|---|---|---|
| EPS | 주당순이익 | 이익 기반 valuation |
| PER | 주가/주당순이익 | 낮을수록 value score 개선 |
| BPS | 주당순자산 | PBR 계산/검증 |
| PBR | 주가/주당순자산 | 저PBR value factor |
| 주당배당금 | DPS | 배당 factor |
| 배당수익률 | 배당/주가 | income factor |

### MP_CORE 활용 단계

1차 MVP:

- 개별종목 지표는 있으면 보조 feature로 쓰되, 누락이 많으면 제외한다.
- 가격/거래량/수급/변동성 중심으로 시작한다.

2차 확장:

- `value_score = rank_low(PER) + rank_low(PBR) + rank_high(dividend_yield)`
- 결측이 많은 업종은 중립값 처리 또는 해당 팩터 제외
- value factor는 momentum/quality와 결합해 과최적화 여부를 검증한다.

## 6. 최근 영업일 자동화

원문은 네이버 금융의 증시자금동향 페이지에서 이전 영업일 날짜를 추출해 KRX 조회일자로 사용한다.

Market Pulse에서는 더 안정적인 방식이 필요하다.

| 방법 | 장점 | 단점 | 판단 |
|---|---|---|---|
| 네이버 금융 날짜 크롤링 | 구현 쉬움 | HTML 구조 변경에 취약 | 보조 수단 |
| KRX API 응답 기준 | 데이터 소스와 일치 | 휴장일 처리 로직 필요 | 권장 |
| DB 내 마지막 수집일 + 영업일 calendar | 재현성 높음 | calendar 테이블 필요 | 최종 권장 |

### 권장 구조

```text
trading_calendar
- trade_date
- market
- is_open
- source

collect job:
1. 기준일 요청 없으면 trading_calendar에서 최근 open date 조회
2. KRX/KIS 데이터 수집
3. 수집 성공/실패 로그 저장
```

## 7. 거래소 데이터 정리 규칙

원문은 업종분류 데이터와 개별종목 지표 데이터를 합친 뒤 다음 정리를 수행한다.

1. 중복 컬럼 확인
2. 공통 종목 기준으로 inner join
3. 시가총액 기준 내림차순 정렬
4. 일반적이지 않은 종목 제외
5. 스팩 제외
6. 우선주 제외

### MP_CORE universe filter 반영

| 필터 | 원문 근거 | MP_CORE 규칙 |
|---|---|---|
| 공통 종목만 사용 | 업종/지표 양쪽에 있는 종목만 merge | 가격/마스터/수급 데이터가 모두 있는 종목 우선 |
| 시가총액 정렬 | 대형주부터 정렬 | 기본 universe에서 시가총액 하위 극단값 제외 |
| 스팩 제외 | 종목명에 `스팩` 포함 | `name like '%스팩%'` 제외 |
| 우선주 제외 | 종목코드 끝자리 활용 | 보통주 중심. 우선주는 1차 MVP 제외 |
| 특수종목 제외 | 리츠, 선박펀드, 해외종목 등 | ETF/REITs/ETN/해외상장/펀드는 별도 asset_type으로 분리 |

### 추가로 필요한 필터

- 거래정지 또는 거래량 0 지속 종목 제외
- 신규상장 후 lookback 기간 부족 종목 제외
- 관리종목/투자주의환기종목 제외
- 액면분할/거래정지로 인한 비정상 수익률 점검
- 가격이 지나치게 낮은 동전주 제외 여부 검토

## 8. WICS 섹터정보

원문은 WiseIndex의 `GetIndexComponets` JSON endpoint를 이용해 WICS 섹터 구성종목을 수집한다.

요청 파라미터:

- `ceil_yn`: 실링 여부
- `dt`: 조회일자
- `sec_cd`: 섹터 코드

응답 구조:

- `info`: 섹터 지수 정보
- `list`: 해당 섹터 구성종목
- `sector`: 전체 섹터 코드/이름
- `size`: 대형주/중형주/소형주 정보

### MP_CORE 활용

WICS 데이터는 KRX 업종보다 투자 팩터 구성에 유용할 수 있다.

| 활용 | 설명 |
|---|---|
| 섹터 중립 | 특정 섹터에 후보가 몰리는 것을 제한 |
| 섹터 모멘텀 | 섹터별 최근 수익률/강도 계산 |
| 섹터 리스크 | 섹터별 최대 비중 제한 |
| 시장 breadth | 섹터별 상승 종목 비율 계산 |
| factor normalization | 섹터 내 순위로 value/momentum score 계산 |

### 주의

- WiseIndex endpoint는 공식 Open API가 아닐 수 있으므로 운영 의존도를 낮춰야 한다.
- 요청 간 `sleep`을 둬야 하며, 과도한 호출은 피한다.
- WICS/GICS 라이선스와 재배포 가능성을 확인해야 한다.
- 서비스 화면에 섹터 데이터를 노출할 경우 출처/라이선스 검토가 필요하다.

## 10. MP_CORE에 필요한 DB 보강

### 10.1 stock_universe_snapshot

일자별 universe 판단 결과를 저장한다.

```sql
CREATE TABLE stock_universe_snapshot (
    id BIGSERIAL PRIMARY KEY,
    trade_date DATE NOT NULL,
    stock_code VARCHAR(20) NOT NULL,
    stock_name VARCHAR(100),
    market VARCHAR(10),
    sector VARCHAR(100),
    market_cap BIGINT,
    avg_trade_amount_20d BIGINT,
    is_common_stock BOOLEAN,
    is_spac BOOLEAN,
    is_preferred BOOLEAN,
    is_tradable BOOLEAN,
    exclude_reason VARCHAR(200),
    created_at TIMESTAMP DEFAULT NOW(),
    CONSTRAINT uq_stock_universe_snapshot UNIQUE (trade_date, stock_code)
);
```

### 10.2 stock_valuation_snapshot

KRX 개별종목 지표 또는 향후 재무 API에서 받은 valuation 값을 저장한다.

```sql
CREATE TABLE stock_valuation_snapshot (
    id BIGSERIAL PRIMARY KEY,
    base_date DATE NOT NULL,
    stock_code VARCHAR(20) NOT NULL,
    eps NUMERIC(18,4),
    per NUMERIC(18,4),
    bps NUMERIC(18,4),
    pbr NUMERIC(18,4),
    dividend_per_share NUMERIC(18,4),
    dividend_yield NUMERIC(18,6),
    source VARCHAR(50),
    created_at TIMESTAMP DEFAULT NOW(),
    CONSTRAINT uq_stock_valuation_snapshot UNIQUE (base_date, stock_code, source)
);
```

### 10.3 sector_classification_snapshot

KRX 업종과 WICS 섹터를 동시에 관리한다.

```sql
CREATE TABLE sector_classification_snapshot (
    id BIGSERIAL PRIMARY KEY,
    base_date DATE NOT NULL,
    stock_code VARCHAR(20) NOT NULL,
    source VARCHAR(20) NOT NULL, -- KRX | WICS
    sector_code VARCHAR(30),
    sector_name VARCHAR(100),
    sector_weight NUMERIC(12,6),
    created_at TIMESTAMP DEFAULT NOW(),
    CONSTRAINT uq_sector_classification_snapshot UNIQUE (base_date, stock_code, source)
);
```

## 11. 구현 우선순위

| 우선순위 | 작업 | 이유 |
|---|---|---|
| 1 | `stock_master`와 `market_daily_price`의 시장/섹터/시총 정합성 점검 | universe 기반 |
| 2 | 스팩/우선주/특수종목 제외 규칙 확정 | 백테스트 왜곡 방지 |
| 3 | 거래대금 상위 universe snapshot 생성 | `MP_CORE` 후보군 고정 |
| 4 | valuation snapshot 가능 여부 확인 | Value factor 2차 확장 |
| 5 | WICS 섹터 수집 가능성/라이선스 확인 | 섹터 중립/섹터 모멘텀 |
| 6 | 최근 영업일 calendar 테이블 도입 | 자동 수집 안정화 |
| 7 | raw/clean/snapshot 계층 분리 | 재현성과 오류 추적 |

## 12. MP_CORE 반영 결론

이 글은 `MP_CORE` 모델의 성능이 알고리즘 이전에 universe 품질에 크게 좌우된다는 점을 보여준다.

따라서 첫 모델 구현 전 아래 결정을 먼저 해야 한다.

- KOSPI/KOSDAQ 보통주만 대상으로 할지
- 우선주, 스팩, 리츠, ETF, ETN, 해외상장 종목을 어떻게 분리할지
- 시가총액 하한과 거래대금 하한을 얼마로 둘지
- KRX 업종과 WICS 중 어떤 섹터 체계를 모델/화면에 사용할지
- PER/PBR/EPS/BPS 같은 KRX 개별지표를 MVP에 포함할지, 2차로 미룰지
- 최근 영업일과 휴장일을 어떤 기준으로 관리할지

`MP_CORE`의 1차 universe는 다음처럼 잡는 것이 적절하다.

```text
KOSPI/KOSDAQ 보통주
AND 스팩/우선주/펀드/ETN/ETF/해외상장 제외
AND 최근 20영업일 평균 거래대금 상위 300개
AND lookback 계산에 필요한 거래일 수 충족
AND 거래정지/결측/비정상 가격 데이터 제외
```
