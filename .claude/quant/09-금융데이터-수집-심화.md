> 출처: 현율, *R을 이용한 퀀트 투자 포트폴리오 만들기(개정판)*, [Chapter 6 금융 데이터 수집하기 (심화)](https://hyunyulhenry.github.io/quant_cookbook/%EA%B8%88%EC%9C%B5-%EB%8D%B0%EC%9D%B4%ED%84%B0-%EC%88%98%EC%A7%91%ED%95%98%EA%B8%B0-%EC%8B%AC%ED%99%94.html)

## 1. 글의 핵심

이 장은 국내 주식 퀀트 모델에 필요한 심화 데이터인 수정주가, 재무제표, 가치지표, DART 공시/재무 데이터를 수집하는 방법을 다룬다.

Market Pulse의 `MP_CORE` 관점에서 핵심은 다음과 같다.

- 가격 피처와 백테스트에는 단순 종가보다 수정주가 기준 데이터가 더 적합하다.
- 재무제표와 가치지표는 Value/Quality 팩터의 필수 입력이다.
- FnGuide Company Guide는 재무제표와 가치지표 계산에 유용하지만, 크롤링/라이선스/안정성 이슈가 있다.
- DART Open API는 무료로 공시와 재무제표를 받을 수 있으나, corp_code 매핑, 계정 표준화, 금융업 예외, 시점 관리가 필요하다.
- `MP_CORE` MVP는 가격/수급 중심으로 시작하고, 이 문서의 재무/공시 데이터는 2차 확장으로 두는 것이 현실적이다.

## 3. 수정주가 수집

원문은 네이버 금융의 fchart endpoint를 이용해 수정주가를 수집한다.

```text
https://fchart.stock.naver.com/siseJson.nhn
  ?symbol=005930
  &requestType=1
  &startTime=YYYYMMDD
  &endTime=YYYYMMDD
  &timeframe=day
```

응답에는 날짜, 시가, 고가, 저가, 종가, 거래량, 외국인소진율 등이 포함된다. 원문은 이 데이터가 수정주가 기준이라고 설명한다.

### 중요 클렌징

- 종목코드는 반드시 6자리 문자열로 유지한다. CSV/엑셀을 거치면 `005930`이 `5930`으로 변할 수 있다.
- 날짜 문자열에서 불필요한 문자를 제거하고 `YYYY-MM-DD` 날짜 타입으로 변환한다.
- 결측 행은 제거하거나 별도 오류로 기록한다.
- 전 종목 반복 수집 시 오류가 나도 전체 작업이 멈추지 않도록 예외처리한다.
- 과도한 요청 방지를 위해 호출 간 sleep을 둔다.

### MP_CORE 적용

현재 프로젝트는 KRX/KIS 기반 `market_daily_price`를 사용하고 있으므로, 네이버 fchart를 주 데이터 소스로 쓰기보다는 보조 검증 소스로 둔다.

필수 결정:

- `market_daily_price.close_price`가 수정주가인지 확인해야 한다.
- 수정주가가 아니라면 수익률/모멘텀/백테스트가 왜곡될 수 있다.
- 수정주가 확보가 어렵다면 액면분할/무상증자 등 corporate action 조정 로직이 필요하다.

## 4. 전 종목 가격 수집 운영 규칙

원문은 for loop로 전 종목 주가를 받으며 `tryCatch`와 `Sys.sleep(2)`를 사용한다.

Market Pulse에서는 아래 운영 규칙으로 바꾼다.

| 원문 개념 | Market Pulse 구현 원칙 |
|---|---|
| for loop | batch job 또는 scheduler |
| tryCatch | 종목별 실패 로그 저장 후 다음 종목 진행 |
| sleep | API rate limit 정책 |
| CSV 저장 | PostgreSQL raw/clean table 저장 |
| 빈 xts 저장 | 실패 상태 row 또는 collect log |

필요 테이블 후보:

```sql
CREATE TABLE quant_collect_log (
    id BIGSERIAL PRIMARY KEY,
    source VARCHAR(50) NOT NULL,
    data_type VARCHAR(50) NOT NULL,
    target_code VARCHAR(20),
    from_date DATE,
    to_date DATE,
    status VARCHAR(20) NOT NULL,
    message TEXT,
    started_at TIMESTAMP DEFAULT NOW(),
    finished_at TIMESTAMP
);
```

위험:

따라서 운영 우선순위는 다음이 적절하다.

1. DART Open API로 무료 재무제표 원천 적재
2. 필요한 경우 FnSpace/FnGuide 유료 API 검토
3. FnGuide 웹 크롤링은 연구용/임시 검증으로 제한

## 6. 가치지표 계산

원문은 재무제표와 현재 주가, 발행주식수를 이용해 가치지표를 계산한다.

| 지표 | 분자 | 분모 |
|---|---|---|
| PER | 주가 | 주당순이익 |
| PBR | 주가 | 주당순자산 |
| PCR | 주가 | 주당영업현금흐름 |
| PSR | 주가 | 주당매출액 |

계산 구조:

```text
value = price / (financial_value * 100000000 / common_share_count)
```

원문에서 재무 데이터는 억 원 단위, 주가는 원 단위라서 단위 변환이 필요하다. 음수 가치지표는 NA 처리한다.

### MP_CORE 적용

Value factor는 아래처럼 만든다.

```text
per_score = rank_low(PER)
pbr_score = rank_low(PBR)
pcr_score = rank_low(PCR)
psr_score = rank_low(PSR)
value_score = average(valid scores)
```

주의:

- 음수 PER/PCR은 단순히 저평가로 보면 안 된다.
- 업종별 valuation 수준이 다르므로 전체 순위와 섹터 내 순위를 함께 봐야 한다.
- 재무제표 발표 시점 이후에만 해당 값을 사용해야 한다.
- 현재가로 과거 가치지표를 계산하면 look-ahead bias가 생긴다. 과거 시점 valuation은 해당 시점 주가와 당시 사용 가능했던 재무제표로 계산해야 한다.

## 7. DART Open API

DART는 금융감독원 전자공시시스템이며, API를 통해 기업 고유번호, 공시검색, 사업보고서 주요정보, 재무제표를 수집할 수 있다.

### 7.1 API Key

원문은 R의 `.Renviron`에 API key를 저장한다.

Market Pulse에서는 아래 원칙을 적용한다.

- `application.yml`에 직접 키를 쓰지 않는다.
- 환경변수 또는 `application-local.yml`/운영 secret으로 관리한다.
- 호출량, 실패, 응답 메시지를 collect log에 남긴다.

### 7.2 corp_code 다운로드

DART API는 기업 식별자로 8자리 `corp_code`를 사용한다. 따라서 주식 6자리 코드와 DART corp_code를 매핑해야 한다.

원문의 corpCode.xml 주요 필드:

| 필드 | 의미 |
|---|---|
| corp_code | DART 고유번호 |
| corp_name | 기업명 |
| stock_code | 거래소 상장 종목코드 |

Market Pulse 필요 테이블:

```sql
CREATE TABLE dart_corp_code (
    corp_code VARCHAR(8) PRIMARY KEY,
    corp_name VARCHAR(200) NOT NULL,
    stock_code VARCHAR(20),
    updated_at TIMESTAMP DEFAULT NOW()
);
CREATE INDEX idx_dart_corp_stock_code ON dart_corp_code(stock_code);
```

## 8. DART 공시검색

원문은 `list.json` API를 사용해 전체 공시 또는 특정 기업 공시를 가져온다.

주요 파라미터:

- `bgn_de`: 시작일
- `end_de`: 종료일
- `corp_code`: 특정 기업 조회 시 사용
- `page_no`, `page_count`: 페이지 처리

주요 응답:

- `corp_code`
- `corp_name`
- `stock_code`
- `report_nm`
- `rcept_no`
- `rcept_dt`

### MP_CORE 활용

공시 데이터는 MVP 핵심 피처는 아니지만, 리스크 플래그와 이벤트 필터에 유용하다.

활용 예:

- 유상증자, 전환사채, 횡령/배임, 거래정지 관련 공시 감지
- 실적 발표/잠정실적 공시 이벤트
- IR 개최, 대량보유상황보고서, 주요주주 변동
- 공시 발생 후 단기 변동성 확대 리스크 플래그

필요 테이블 후보:

```sql
CREATE TABLE dart_disclosure (
    id BIGSERIAL PRIMARY KEY,

    stock_code VARCHAR(20),
    corp_name VARCHAR(200),
    report_name TEXT NOT NULL,
    receipt_no VARCHAR(30) NOT NULL UNIQUE,
    filer_name VARCHAR(200),
    receipt_date DATE,

    created_at TIMESTAMP DEFAULT NOW()
);
```

## 10. DART 재무정보

DART는 주요계정, 다중회사 주요계정, 단일회사 전체 재무제표를 제공한다.

| API | 용도 | MP_CORE 판단 |
|---|---|---|
| `fnlttSinglAcnt.json` | 단일회사 주요계정 | 기본 재무 factor에 충분 |
| `fnlttMultiAcnt.json` | 여러 회사 주요계정 | 대량 수집 효율 개선 |
| `fnlttSinglAcntAll.json` | 단일회사 전체 재무제표 | 상세 factor/품질 factor 확장 |

전체 재무제표의 주요 필드:

- `corp_code`
- `sj_nm`: 재무제표명
- `account_nm`: 계정명
- `account_detail`
- `thstrm_amount`: 당기
- `frmtrm_amount`: 전기
- `bfefrmtrm_amount`: 전전기

### CFS/OFS 처리

원문은 연결재무제표(`CFS`)가 없으면 개별재무제표(`OFS`)로 재요청한다.

Market Pulse에서도 같은 fallback이 필요하다.

```text
1. CFS 요청
2. 응답 list 없음 → OFS 요청
3. 둘 다 없음 → 실패 로그 저장
```

### 금융주 예외

원문은 일부 종목, 특히 금융주는 API 파일이 제공되지 않는 경우가 있다고 언급한다.

따라서 `MP_CORE`의 재무 factor는 다음 중 하나를 선택해야 한다.

- 금융주를 재무 factor 계산에서 제외
- 금융주 전용 계정 매핑을 별도 설계
- 재무 factor 결측을 중립값으로 처리

## 11. 시점 관리와 look-ahead bias

심화 데이터에서 가장 중요한 문제는 시점 관리다.

잘못된 예:

```text
2019년 사업보고서 숫자를 2019-12-31 이전 신호에 사용
현재 주가로 과거 PER/PBR 계산
공시 발표일 이전에 공시 내용을 feature로 사용
```

필수 규칙:

- 재무제표는 `rcept_dt` 또는 공시일 이후 신호일부터 사용한다.
- 가치지표의 주가는 신호일 기준 가격을 사용한다.
- 발행주식수도 해당 시점에 알려진 값을 사용한다.
- 분기/연간 데이터의 발표 지연을 반영한다.
- feature snapshot에는 사용한 source date와 report date를 남긴다.

## 12. MP_CORE 데이터 확장 로드맵

### 1차 MVP

- KRX/KIS 가격, 거래량, 거래대금, 시가총액
- 외국인/기관 수급
- 시장 국면
- 수정주가 여부 점검

### 2차 Value/Quality 확장

- DART corp_code 매핑
- DART 주요계정 수집
- PER/PBR/PCR/PSR 계산
- ROE, 부채비율, 매출성장률, 이익안정성 계산
- 재무제표 공시일 기준 시점 관리

### 3차 이벤트/공시 확장

- DART 공시검색 적재
- report name 기반 이벤트 분류
- 위험 공시 플래그
- 실적 발표/잠정실적 이벤트 factor

### 4차 대체/유료 데이터

- FnSpace/FnGuide 유료 API 검토
- 컨센서스/목표가/추정실적
- PEAD/어닝 서프라이즈 모델

## 13. 추천 DB 설계

### 13.1 financial_statement_raw

```sql
CREATE TABLE financial_statement_raw (
    id BIGSERIAL PRIMARY KEY,
    corp_code VARCHAR(8) NOT NULL,
    stock_code VARCHAR(20),
    business_year INTEGER NOT NULL,
    report_code VARCHAR(10) NOT NULL,
    fs_div VARCHAR(10), -- CFS | OFS
    statement_name VARCHAR(100),
    account_name VARCHAR(200),
    account_detail TEXT,
    current_amount NUMERIC(24,4),
    previous_amount NUMERIC(24,4),
    before_previous_amount NUMERIC(24,4),
    receipt_no VARCHAR(30),
    source VARCHAR(30) NOT NULL DEFAULT 'DART',
    raw_json JSONB,
    created_at TIMESTAMP DEFAULT NOW()
);
```

### 13.2 financial_factor_snapshot

```sql
CREATE TABLE financial_factor_snapshot (
    id BIGSERIAL PRIMARY KEY,
    base_date DATE NOT NULL,
    available_from DATE NOT NULL,
    stock_code VARCHAR(20) NOT NULL,
    per NUMERIC(18,6),
    pbr NUMERIC(18,6),
    pcr NUMERIC(18,6),
    psr NUMERIC(18,6),
    roe NUMERIC(18,6),
    debt_to_equity NUMERIC(18,6),
    sales_growth NUMERIC(18,6),
    earnings_stability NUMERIC(18,6),
    source VARCHAR(30),
    created_at TIMESTAMP DEFAULT NOW(),
    CONSTRAINT uq_financial_factor_snapshot UNIQUE (base_date, stock_code, source)
);
```

### 13.3 corporate_action_adjustment

수정주가 검증 또는 자체 보정이 필요할 경우 사용한다.

```sql
CREATE TABLE corporate_action_adjustment (
    id BIGSERIAL PRIMARY KEY,
    stock_code VARCHAR(20) NOT NULL,
    action_date DATE NOT NULL,
    action_type VARCHAR(50),
    adjustment_factor NUMERIC(18,10),
    source VARCHAR(50),
    created_at TIMESTAMP DEFAULT NOW()
```

## 14. 구현 우선순위

| 우선순위 | 작업 | 이유 |
|---|---|---|
| 1 | `market_daily_price` 수정주가 여부 확인 | 모든 수익률/백테스트의 기반 |
| 2 | 종목코드 6자리 문자열 보존 점검 | DART/KRX/KIS join 오류 방지 |
| 3 | DART corp_code 매핑 테이블 구축 | 재무/공시 API 선행조건 |
| 4 | DART 주요계정 수집 PoC | Value/Quality factor 가능성 검증 |
| 5 | 재무제표 시점 관리 규칙 확정 | look-ahead bias 방지 |
| 6 | 가치지표 계산 테이블 설계 | PER/PBR/PCR/PSR factor |
| 7 | 공시검색 적재 | 이벤트/위험 플래그 |
| 8 | FnGuide/FnSpace 유료 데이터 검토 | 컨센서스/표준화 재무 품질 개선 |

## 15. MP_CORE 반영 결론

이 문서는 `MP_CORE`가 단기 가격/수급 모델에서 장기적으로 `Fundamental Quant` 모델로 확장되기 위해 필요한 데이터 경로를 보여준다.

핵심 결정:

- 1차 모델은 재무 데이터를 기다리지 않고 가격/수급/변동성으로 시작한다.
- 단, 가격 데이터가 수정주가 기준인지 반드시 확인한다.
- 재무 factor는 DART 기반으로 먼저 붙이는 것이 운영상 안전하다.
- FnGuide 웹 크롤링은 연구 참고로만 두고, 운영 데이터 소스로 쓰려면 라이선스와 안정성을 따로 확인한다.
- 재무 데이터는 공시일 이후부터만 feature로 사용해야 한다.
- Value/Quality factor를 붙이면 월 15% 목표 달성 가능성을 높일 수 있지만, 동시에 결측/시점/업종별 왜곡 관리가 필요하다.
