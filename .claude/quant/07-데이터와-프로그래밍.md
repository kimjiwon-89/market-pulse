## 1. 글의 핵심

퀀트 투자는 데이터 과학을 금융에 적용한 사례다. 데이터를 수집하고, 정리하고, 가공하고, 시각화하고, 모델링한 뒤, 그 결과를 바탕으로 투자와 성과 평가를 수행한다.

Market Pulse의 `MP_CORE` 모델 관점에서는 다음 메시지가 중요하다.

- 퀀트 모델의 중심은 데이터와 프로그래밍이다.
- 원천 데이터는 바로 투자에 쓸 수 있는 형태가 아니므로 클렌징과 정규화가 필수다.
- 엑셀은 소규모 실험에는 가능하지만, 종목 수와 전략 수가 늘어나면 프로그래밍이 필수다.
- 백테스트와 전략 실험은 코드화해야 파라미터 변경, 반복 검증, 재현성이 확보된다.
- R 생태계의 패키지 구조는 Python/Spring 기반 Market Pulse에서도 그대로 대응 개념을 설계할 수 있다.

## 2. 퀀트 투자와 데이터 과학의 공통 흐름

글에서 설명하는 데이터 과학 업무 흐름은 퀀트 투자 프로세스와 거의 같다.

```text
데이터 불러오기
→ 데이터 정리
→ 데이터 변형
→ 시각화
→ 모델링
→ 결과 공유/소통
```

퀀트 투자에서는 위 흐름이 아래처럼 바뀐다.

```text
주가/재무/수급 데이터 수집
→ 결측/이상치/코드/날짜 정리
→ 수익률, 변동성, 팩터 지표 계산
→ 데이터 특징과 분포 확인
→ 종목 선정, scoring, 백테스트
→ 신호, 포트폴리오, 성과 리포트 제공
```

## 3. 데이터 구하기

### 3.1 유료 데이터

글에서는 해외 데이터에 Bloomberg, FactSet, 국내 데이터에 DataGuide를 언급한다. 이런 데이터 제공업체는 데이터 수집뿐 아니라 백테스트와 성과 평가 도구까지 제공하지만, 비용이 높다는 단점이 있다.

Market Pulse 적용:

- 초기에는 KRX/KIS 무료 API와 현재 DB를 최대한 활용한다.
- 재무/컨센서스/팩터 데이터가 필요해지는 단계에서 FnGuide, FnSpace, DataGuide 같은 유료 소스를 검토한다.
- 유료 데이터 도입 전에는 “가격/거래량/수급/시장국면” 중심 모델로 범위를 제한한다.

### 3.2 해외 저비용 데이터

글에서는 Quandl, Tiingo 같은 해외 데이터 서비스를 언급한다. API로 직접 데이터를 받을 수 있다는 점이 장점이지만, 한국 시장 데이터는 제한적이다.

Market Pulse 적용:

- 한국 주식 중심 `MP_CORE`에는 직접 적용성이 낮다.
- 향후 미국 ETF/글로벌 자산배분 모델을 붙일 때 후보 데이터 소스로 검토한다.

### 3.3 국내 무료 데이터

국내 데이터를 무료로 얻으려면 국내 금융 웹사이트나 거래소 데이터를 크롤링/API로 수집하고, 직접 클렌징해야 한다.

Market Pulse 적용:

- 현재 프로젝트는 KRX Open API, KIS Open API, `market_daily_price`, `stock_master`를 기반으로 한다.
- 무료 데이터의 핵심 리스크는 데이터 정합성, 결측, 상장폐지/관리종목 데이터, 수정주가 처리다.
- 데이터 클렌징과 시점 관리 없이는 모델 성과가 과대평가될 수 있다.

## 4. 왜 프로그래밍이 필요한가

글의 핵심 주장은 명확하다. 데이터 수집, 클렌징, 백테스트, 종목 선정은 반복 작업이 많고, 데이터와 전략 규모가 커질수록 엑셀로는 비효율적이다.

### 엑셀의 한계

- 종목 수가 많아지면 수작업 처리 불가능
- 파라미터 변경 시 계산식을 반복 수정해야 함
- 전략이 늘어날수록 파일이 중복되고 관리가 어려움
- 데이터 업데이트 시 모든 파일을 다시 갱신해야 함
- 속도와 재현성 문제가 커짐

### 프로그래밍의 장점

- 원본 데이터 하나를 여러 전략이 공유할 수 있음
- 파라미터만 바꿔 반복 백테스트 가능
- 전략 로직을 코드로 보존해 재현 가능
- 데이터 변경 시 파이프라인을 다시 실행하면 됨
- 대규모 종목과 긴 기간 데이터를 자동 처리 가능

### MP_CORE 설계 반영

`MP_CORE`는 엑셀형 분석이 아니라 아래 구조가 필요하다.

```text
raw data table
→ cleaning/normalization job
→ feature snapshot
→ train/test split
→ model artifact
→ signal table
→ backtest run
→ trade list/report
```

## 5. R과 Python 선택에 대한 판단

원문은 R을 기준으로 설명한다. R은 통계/계량분석/시계열/포트폴리오 분석 패키지가 풍부하고, 퀀트 연구에 적합하다.

Market Pulse에서는 이미 백엔드가 Spring Boot이고, 머신러닝 자료가 scikit-learn 중심이므로 다음 구조가 더 자연스럽다.

| 역할 | 원문 R 생태계 | Market Pulse 대응 |
|---|---|---|
| 데이터 수집 | quantmod, httr, rvest | Spring/KRX/KIS API, Python requests 보조 |
| 데이터 정리 | dplyr, tidyr | SQL, Java service, Python pandas |
| 시계열 | xts, zoo | pandas time series, SQL date index |
| 모델링 | R 통계 패키지 | scikit-learn RandomForest, LogisticRegression |
| 성과 평가 | PerformanceAnalytics | Java/Python 성과 계산, 프론트 Recharts |
| 시각화 | ggplot2 | React/Recharts, Python plot 보조 |

결론:

- R의 개념과 패키지 구조는 참고하되, 구현은 Python + Spring Boot + PostgreSQL로 간다.
- Python은 학습/실험/feature 검증에 쓰고, Spring은 API/DB/운영 화면을 맡는다.

## 6. 유용한 R 패키지와 MP_CORE 대응 개념

| R 패키지 | 원문 용도 | MP_CORE 대응 |
|---|---|---|
| `quantmod` | API 데이터 다운로드, 기술적 지표, 차트 | KRX/KIS 수집기, Python technical indicator 계산 |
| `PerformanceAnalytics` | 포트폴리오 성과/위험 측정, `Return.portfolio()` | backtest engine, MDD/Sharpe/승률/월별수익률 계산 |
| `xts` | 금융 시계열 데이터 처리, 월/연 단위 변환 | `market_daily_price` 날짜 인덱스, pandas resample |
| `zoo` | rolling window, 결측 보정 | rolling return/volatility, `na.locf` 대응 결측 처리 |
| `httr` | GET/POST HTTP 요청 | KRX POST API, KIS GET API client |
| `rvest` | HTML 크롤링 | 필요 시 Jsoup/Python BeautifulSoup |
| `dplyr` | 데이터 정리, 필터, 집계 | SQL mapper, pandas transform, Java stream |
| `ggplot2` | 데이터 시각화 | React/Recharts, HTML 리포트 |

## 7. 데이터 클렌징 체크리스트

원문은 데이터가 바로 투자에 쓸 수 있는 형태가 아니라고 강조한다. `MP_CORE`에서는 아래 항목을 반드시 확인해야 한다.

| 항목 | 체크 내용 | 실패 시 영향 |
|---|---|---|
| 날짜 정렬 | 모든 종목/지수가 거래일 기준으로 정렬되는가 | forward return, rolling feature 오류 |
| 결측치 | 가격, 거래량, 시가총액 결측 처리 기준이 있는가 | 잘못된 수익률/변동성 |
| 수정주가 | 액면분할, 무상증자, 배당락 영향 반영 여부 | 과거 수익률 왜곡 |
| 상장폐지 | survivorship bias 여부 | 백테스트 과대평가 |
| 신규상장 | lookback 기간 부족 종목 제외 여부 | 모멘텀/변동성 계산 오류 |
| 거래정지 | 거래량 0, 가격 고정 종목 처리 | 체결 불가능 신호 발생 |
| 시장 구분 | KOSPI/KOSDAQ/ETF/INDEX 구분 정확성 | universe 오염 |
| 통화/단위 | 원, 억, 주, %, 소수 변환 일관성 | feature scale 오류 |
| 시점 관리 | 신호일 이후 데이터를 feature에 쓰지 않는가 | look-ahead bias |

## 8. MP_CORE 데이터 파이프라인 제안

### 8.1 Raw Layer

원천 데이터를 가능한 한 원형에 가깝게 보관한다.

```text
krx_raw_daily_stock
krx_raw_daily_index
kis_raw_investor_flow
stock_master
```

목적:

- 원천 오류 추적
- 재처리 가능성 확보
- API 변경 대응

### 8.2 Clean Layer

투자 모델에 쓸 수 있는 표준 형태로 정리한다.

```text
market_daily_price
investor_daily_flow
stock_universe_status
```

목적:

- 날짜/종목코드/시장 구분 통일
- 결측/이상치 처리
- 거래 가능 universe 판단

### 8.3 Feature Layer

학습과 신호 생성에 사용한 시점별 feature를 저장한다.

```text
quant_core_feature_snapshot
```

목적:

- 재현성 확보
- 학습 데이터와 실시간 신호 데이터의 schema 일치
- look-ahead bias 방지

### 8.4 Model Layer

학습 산출물을 버전으로 관리한다.

```text
quant_model_version
models/quant/mp_core/{version}/model.joblib
models/quant/mp_core/{version}/metadata.json
```

목적:

- 어떤 데이터와 파라미터로 학습했는지 추적
- 모델 롤백 가능
- 성과 비교 가능

### 8.5 Signal/Backtest Layer

실제 투자 판단과 성과를 저장한다.

```text
quant_core_signal
quant_core_backtest_run
quant_trade_log
```

목적:

- 날짜별 추천 종목과 비중 저장
- 백테스트 결과 재조회
- 트레이드 리스트 생성

## 9. 프로그래밍 단위 작업

원문의 "프로그래밍은 반복 작업을 자동화한다"는 메시지를 기준으로, `MP_CORE`의 코드는 아래 단위로 나눠야 한다.

| 작업 | 설명 | 권장 구현 |
|---|---|---|
| 수집 | KRX/KIS에서 가격/수급 데이터 저장 | Spring scheduler/service |
| 정리 | 결측, 단위, 날짜, 종목 상태 정규화 | SQL + Java service |
| 피처 생성 | rolling return, volatility, beta, RSI 등 | Python pandas 또는 Java service |
| 학습 | train/validation/test 분리, Random Forest fitting | Python scikit-learn |
| 평가 | precision, recall, MDD, Sharpe, monthly return | Python + Java DTO |
| 신호 생성 | 최신 feature로 상승확률/랭킹 계산 | Python model load + Spring API |
| 백테스트 | 체결가, 비용, 손절/익절, 리밸런싱 | Java backtest engine |
| 화면 제공 | 모델 상태, 신호, 성과, trade list | React |

## 10. 현재 프로젝트에 대한 함의

### 이미 맞는 방향

- `market_daily_price`로 가격 데이터를 중앙화하려는 구조가 있다.
- `/api/quant/collect`로 수집 작업을 API화하고 있다.
- 백테스트 결과와 매매 로그 테이블 구조가 이미 있다.
- React 화면에서 equity, allocation, trade timeline을 보여주는 구조가 있다.

### 부족한 부분

- raw layer와 clean layer가 명확히 분리되어 있지 않다.
- feature snapshot이 없어 학습/신호 재현성이 약하다.
- 모델 버전 관리가 없다.
- Python 학습 스크립트와 Java API 사이의 계약이 아직 없다.
- 데이터 클렌징 리포트가 없다.
- 수정주가/상장폐지/거래정지/관리종목 처리 기준이 더 필요하다.

## 11. MP_CORE 구현 전 데이터 준비 우선순위

| 우선순위 | 작업 | 이유 |
|---|---|---|
| 1 | `market_daily_price` 적재 상태 점검 | 모델의 기본 입력 데이터 |
| 2 | 거래일 calendar 확정 | rolling feature와 forward label 계산 기준 |
| 3 | 결측/거래정지 필터 정의 | 체결 불가능 신호 방지 |
| 4 | 수정주가 처리 기준 확인 | 수익률 왜곡 방지 |
| 5 | 종목별 수급 데이터 확장 | behavioral/flow factor 구현 |
| 6 | feature snapshot 테이블 설계 | 재현성, 검증, 운영 안정성 |
| 7 | Python 학습 환경 고정 | scikit-learn 버전, 모델 artifact 호환성 |
| 8 | 성과 평가 지표 표준화 | 월 15% 목표 판단의 기준 통일 |

## 12. 결론

이 글은 `MP_CORE`에서 가장 먼저 해야 할 일이 모델 알고리즘 선택이 아니라 데이터와 프로그래밍 파이프라인 정비라는 점을 확인시켜준다.

즉, Random Forest 자체보다 더 중요한 것은 아래다.

- 데이터가 정확히 수집되는가
- 모델이 보는 데이터가 신호일 기준 과거 데이터뿐인가
- 피처와 레이블을 재현할 수 있는가
- 파라미터 변경과 백테스트를 코드로 반복할 수 있는가
- 성과와 위험을 같은 기준으로 평가하는가

따라서 `MP_CORE`는 "전략 코드 하나"가 아니라 데이터 수집, 클렌징, feature snapshot, 모델 버전, 신호, 백테스트, 성과 리포트가 연결된 하나의 파이프라인으로 설계해야 한다.
