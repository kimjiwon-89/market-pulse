# 데이터 정리하기

> 출처: 현율, *R을 이용한 퀀트 투자 포트폴리오 만들기(개정판)*, [Chapter 7 데이터 정리하기](https://hyunyulhenry.github.io/quant_cookbook/%EB%8D%B0%EC%9D%B4%ED%84%B0-%EC%A0%95%EB%A6%AC%ED%95%98%EA%B8%B0.html)
> 정리일: 2026-05-20

## 1. 글의 핵심

이 장은 앞 장에서 종목별 CSV로 흩어져 저장한 주가, 재무제표, 가치지표 데이터를 모델 입력으로 쓰기 좋게 하나의 정리된 데이터셋으로 합치는 과정을 다룬다.

Market Pulse의 `MP_CORE` 관점에서 핵심은 다음과 같다.

- 종목별 파일 단위 데이터는 연구 초기에는 편하지만, 백테스트와 모델 학습에는 통합 테이블이 필요하다.
- 주가 데이터는 날짜 x 종목 형태의 wide matrix로 만들 수 있으나, 운영 DB에서는 `trade_date + asset_code` long table이 더 적합하다.
- 재무제표는 종목마다 계정 항목이 다르므로 기준 계정 목록, 누락 처리, 연도 정렬 규칙이 필요하다.
- 가치지표는 PER/PBR/PCR/PSR처럼 모델에 바로 쓰는 팩터 후보지만, `Inf`, 음수, 결측, 발표 시점 문제를 함께 처리해야 한다.
- 원문은 R/CSV/RDS 중심이지만, Market Pulse는 PostgreSQL 적재와 API 응답을 기준으로 같은 정리 원칙을 구현해야 한다.

## 2. 정리 대상과 산출물

| 데이터 | 원문 입력 | 원문 산출물 | Market Pulse 적용 |
|---|---|---|---|
| 주가 | `data/KOR_price/{ticker}_price.csv` | `data/KOR_price.csv` | `market_daily_price` 정제 row |
| 재무제표 | `data/KOR_fs/{ticker}_fs.csv` | `data/KOR_fs.Rds` | 재무 raw/standardized table 후보 |
| 가치지표 | `data/KOR_value/{ticker}_value.csv` | `data/KOR_value.csv` | value factor table 또는 feature view |

원문의 공통 전제는 `KOR_ticker.csv`에 있는 종목코드를 6자리 문자열로 맞춘 뒤, 해당 종목코드로 개별 파일을 찾아 읽는 구조다.

## 3. 주가 정리

원문은 종목별 가격 CSV를 모두 읽어서 `xts` 시계열로 변환한 뒤, 열 방향으로 결합한다. 이후 결측치는 직전 값을 이어붙이는 방식으로 채운다.

핵심 절차:

1. 종목코드를 6자리 문자열로 보정한다.
2. 종목별 가격 파일을 반복해서 읽는다.
3. 각 가격 데이터를 시계열 객체로 변환한다.
4. 모든 종목의 가격을 날짜 기준으로 열 결합한다.
5. 결측치는 전일 값으로 보간한다.
6. 열 이름을 종목코드로 지정한다.
7. 최종 데이터를 CSV로 저장한다.

### MP_CORE 적용

Market Pulse는 CSV wide matrix보다 아래 형태의 long table을 기본으로 둔다.

```text
market_daily_price
- trade_date
- asset_code
- asset_type
- asset_name
- market
- sector
- close_price
- open_price
- high_price
- low_price
- trade_volume
- trade_amount
- market_cap
```

wide matrix는 모델 학습이나 상관관계 계산 시 임시 뷰로 만들 수 있다.

```sql
-- 예시: 날짜 x 종목 종가 matrix를 만들 때의 개념
SELECT trade_date, asset_code, close_price
FROM market_daily_price
WHERE asset_type = 'STOCK'
ORDER BY trade_date, asset_code;
```

운영 데이터 정리 규칙:

- `asset_code`는 숫자가 아니라 문자열로 보관한다.
- `trade_date + asset_code + asset_type` unique key를 유지한다.
- 가격이 0이거나 음수인 행은 모델 입력에서 제외한다.
- 거래량/거래대금이 지속적으로 0인 종목은 universe에서 제외한다.
- 결측 보간은 가격 차트 표시와 백테스트 입력을 구분해서 적용한다.

## 4. 주가 결측 처리 판단

원문은 `na.locf()` 방식으로 결측치에 전일 값을 사용한다. 이 방식은 날짜 x 종목 matrix를 만들 때 편하지만, 투자 모델에서는 조심해야 한다.

| 상황 | 전일 값 보간 가능 여부 | 판단 |
|---|---:|---|
| 휴장일 때문에 전체 시장 데이터가 없음 | 낮음 | 거래일 calendar로 제거 |
| 특정 종목 거래정지 | 제한적 | 가격 보간보다 거래 불가 상태로 보는 편이 안전 |
| 신규상장 전 기간 | 불가 | lookback 부족으로 제외 |
| 일시적 API 누락 | 가능 | collect log와 재수집 우선 |
| 차트 표시용 빈 칸 | 가능 | UI용 보간으로만 제한 |

`MP_CORE` 백테스트에서는 보간된 가격으로 매수/매도 체결을 가정하면 결과가 왜곡될 수 있다. 따라서 모델 입력에는 원천 결측 상태를 최대한 보존하고, 보간 여부를 별도 플래그로 남기는 편이 좋다.

필요 컬럼 후보:

```sql
ALTER TABLE market_daily_price
ADD COLUMN IF NOT EXISTS is_imputed BOOLEAN DEFAULT FALSE,
ADD COLUMN IF NOT EXISTS collect_status VARCHAR(20);
```

## 5. 재무제표 정리

원문은 종목별 재무제표 CSV를 리스트로 읽은 뒤, 기준이 되는 재무 항목 목록을 정하고 항목별로 전 종목 데이터를 다시 묶는다.

핵심 절차:

1. 모든 종목의 재무제표 CSV를 리스트로 읽는다.
2. 첫 번째 종목의 행 이름을 기준 재무 항목 목록으로 사용한다.
3. 특정 항목이 각 종목 재무제표에 있으면 해당 행을 선택한다.
4. 없으면 NA 데이터프레임을 넣는다.
5. 종목별 선택 결과를 행 방향으로 결합한다.
6. 불필요한 NA 열을 제거한다.
7. 연도 컬럼을 시간 순서대로 정렬한다.
8. 행 이름을 종목코드로 바꾼다.
9. 항목별 데이터프레임을 리스트에 담고, 리스트 이름을 재무 항목명으로 지정한다.
10. 리스트 구조를 유지하기 위해 RDS로 저장한다.

### 기준 계정 목록의 의미

재무제표는 업종마다 계정 구조가 다르다. 예를 들어 금융업, 제조업, 바이오 기업은 매출/자산/현금흐름 항목의 의미와 계정명이 다를 수 있다.

원문은 첫 번째 종목의 재무 항목을 기준으로 삼아 데이터 폭을 통제한다. 이 방식은 단순하고 빠르지만, 기준 종목에 없는 항목은 전체 데이터셋에서 빠질 수 있다.

Market Pulse에서는 아래처럼 명시적 표준 계정 목록을 두는 편이 안전하다.

| 표준 계정 | 활용 팩터 | 주의 |
|---|---|---|
| 매출액 | 성장성, PSR | 금융업 예외 |
| 영업이익 | 수익성, 이익 모멘텀 | 일회성 비용 확인 필요 |
| 당기순이익 | PER, ROE | 지배/비지배 구분 |
| 자본총계 | PBR, ROE | 자본잠식 처리 |
| 영업활동현금흐름 | PCR, Quality | 음수 처리 |
| 총자산 | ROA, 안정성 | 금융업 스케일 차이 |
| 부채총계 | 레버리지 | 업종별 중립화 필요 |

## 6. 재무제표 DB 설계 후보

원문의 RDS 리스트는 R 분석 환경에서는 편하지만, 서비스 백엔드에서는 검색/조인/버전 관리가 어렵다. PostgreSQL에서는 raw table과 standardized table을 나누는 구조가 좋다.

```sql
CREATE TABLE financial_statement_raw (
    id BIGSERIAL PRIMARY KEY,
    stock_code VARCHAR(10) NOT NULL,
    fiscal_year INTEGER NOT NULL,
    fiscal_period VARCHAR(20) NOT NULL,
    statement_type VARCHAR(30),
    account_name VARCHAR(200) NOT NULL,
    amount NUMERIC(24, 4),
    source VARCHAR(50) NOT NULL,
    collected_at TIMESTAMP DEFAULT NOW()
);

CREATE TABLE financial_statement_standard (
    stock_code VARCHAR(10) NOT NULL,
    fiscal_year INTEGER NOT NULL,
    fiscal_period VARCHAR(20) NOT NULL,
    standard_account VARCHAR(80) NOT NULL,
    amount NUMERIC(24, 4),
    source_account_name VARCHAR(200),
    source VARCHAR(50) NOT NULL,
    updated_at TIMESTAMP DEFAULT NOW(),
    PRIMARY KEY (stock_code, fiscal_year, fiscal_period, standard_account)
);
```

정리 규칙:

- 원천 계정명은 보존한다.
- 표준 계정으로 매핑한 결과를 별도 테이블에 저장한다.
- 결산월, 연결/별도, 연간/분기 구분을 명시한다.
- 공시 발표일 또는 수집 가능일을 저장해 look-ahead bias를 막는다.

## 7. 가치지표 정리

원문은 종목별 가치지표 CSV를 읽고, 행으로 저장된 PER/PBR/PCR/PSR 값을 전치해서 열 형태로 바꾼 뒤 전 종목을 행 방향으로 결합한다.

핵심 절차:

1. 종목별 가치지표 파일을 읽는다.
2. 행 형태 데이터를 전치해 지표가 열이 되도록 바꾼다.
3. 전 종목 데이터를 행 방향으로 결합한다.
4. PER, PBR, PCR, PSR 열만 남긴다.
5. `Inf` 값을 NA로 바꾼다.
6. 행 이름을 종목코드로 지정한다.
7. 최종 CSV로 저장한다.

### Inf 처리의 의미

가치지표에서 `Inf`가 생기는 대표 원인은 분모가 0이기 때문이다.

| 지표 | 분모 | Inf 발생 예 |
|---|---|---|
| PER | EPS | 순이익 0 |
| PBR | BPS | 자본 0 또는 데이터 오류 |
| PCR | 주당 영업현금흐름 | 영업현금흐름 0 |
| PSR | 주당 매출액 | 매출 0 |

`Inf`는 단순히 큰 숫자가 아니라 계산 불능 상태로 보는 것이 적절하다. 원문처럼 NA로 바꾸고, 모델에서는 결측 처리 규칙을 별도로 둔다.

## 8. Value Factor 적용 규칙

`MP_CORE`에서 가치지표는 단독 매수 신호보다는 보조 팩터로 쓰는 편이 적합하다.

기본 스코어링:

```text
per_score = 낮은 PER 순위
pbr_score = 낮은 PBR 순위
pcr_score = 낮은 PCR 순위
psr_score = 낮은 PSR 순위
value_score = 사용 가능한 점수의 평균
```

주의사항:

- PER이 음수인 기업은 저평가가 아니라 적자 기업일 수 있다.
- PBR이 지나치게 낮은 기업은 가치 함정일 수 있다.
- 업종별 적정 valuation이 다르므로 전체 순위와 섹터 내 순위를 구분한다.
- 과거 백테스트에서는 당시 사용 가능했던 재무제표와 당시 가격으로 계산해야 한다.
- 현재 시점 가치지표를 과거 전 구간에 적용하면 look-ahead bias가 생긴다.

추천 결측 처리:

| 상황 | 처리 |
|---|---|
| 지표 계산 불능 | NA |
| 음수 PER/PCR | 별도 플래그 후 value score 제외 검토 |
| 극단치 | winsorizing 또는 분위수 clipping |
| 일부 지표만 존재 | 존재하는 지표만 평균, 최소 지표 개수 조건 적용 |
| 업종 특수성 | sector-neutral rank 병행 |

## 9. 원문 R 코드 개념을 서비스 구조로 바꾸기

| 원문 R 처리 | 의미 | Market Pulse 구현 |
|---|---|---|
| `read.csv()` | 파일 읽기 | API/DB repository read |

| `saveRDS()` | 복합 객체 저장 | normalized table + feature snapshot |
| `write.csv()` | 정리 결과 저장 | PostgreSQL table / materialized view |

## 10. MP_CORE 데이터 정리 파이프라인

권장 흐름:

```text
1. 원천 수집
   KRX/KIS/DART 등 외부 API 호출

2. raw 저장
   원문 응답 JSON 또는 원천 필드를 최대한 보존

3. 표준화
   종목코드, 날짜, 숫자, 시장구분, 업종, 계정명 정리

4. 품질 검사
   중복 key, 결측, 0 가격, 비정상 수익률, 거래량 누락 확인

5. feature 생성
   momentum, volatility, liquidity, value, quality 등 계산

6. snapshot 저장
   백테스트 재현을 위해 특정 기준일의 feature를 고정

7. 모델 학습/백테스트
   look-ahead bias 없이 기준일 이전 데이터만 사용
```

## 11. 품질 검사 체크리스트

### 가격 데이터

- `trade_date + asset_code + asset_type` 중복이 없는가?
- 종목코드가 6자리 문자열로 유지되는가?
- 종가, 시가, 고가, 저가가 음수 또는 0이 아닌가?
- 고가가 저가보다 낮은 비정상 행이 없는가?
- 전일 대비 수익률이 비정상적으로 큰 행을 점검했는가?
- 거래정지/신규상장/상장폐지 구간을 구분했는가?

### 재무 데이터

- 연결/별도 기준이 섞이지 않았는가?
- 연간/분기 데이터가 구분되는가?
- 결산월이 다른 기업을 처리했는가?
- 원천 계정명과 표준 계정명 매핑을 남겼는가?
- 발표일 기준으로 과거 시점 사용 가능 여부를 통제했는가?

### 가치지표

- `Inf`, `NaN`, 음수, 극단치를 별도로 처리했는가?
- 업종별 rank와 전체 rank를 구분했는가?
- 현재 시점 지표를 과거 백테스트에 잘못 적용하지 않았는가?
- 결측이 많은 종목/업종에 대한 제외 기준이 있는가?
