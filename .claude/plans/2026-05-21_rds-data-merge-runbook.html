RDS 데이터 병합 런북

작성일: 2026-05-21 · 목표: 현재 로컬 DB 데이터와 메인 배포 환경의 DB 데이터를 모두 AWS RDS PostgreSQL로 옮기고, 삭제 없이 하나의 데이터셋으로 병합한다.

절대 원칙

  • 원본 DB에는 쓰기 작업 금지. 로컬 DB와 운영 배포 DB는 dump만 뜬다.
  • RDS에 바로 덮어쓰기 금지. 먼저 staging/temp schema에 restore해서 중복과 충돌을 확인한다.
  • TRUNCATE, DROP, DELETE 금지. 병합 완료와 검증 전에는 어떤 데이터도 삭제하지 않는다.
  • 모든 dump 파일은 작업 완료 전까지 보관. 로컬, 운영, RDS 초기 상태 dump를 각각 남긴다.

오늘 할 일 요약

1단계

데이터 출처 확정

로컬 PostgreSQL, 메인 배포 DB, 신규 RDS endpoint를 구분하고 접속 정보를 안전하게 준비한다.

2단계

백업과 dump

세 DB 모두 스키마와 데이터를 dump한다. RDS가 비어 있어도 초기 dump를 남긴다.

3단계

무삭제 병합

staging schema에 restore한 뒤 INSERT ON CONFLICT 또는 선별 upsert로 RDS public schema에 합친다.

대상 데이터 소스

구분 역할 작업 방식 주의사항
로컬 DB 현재 개발 PC에 쌓인 데이터 pg_dump로 schema + data 백업 개발 중 생성한 quant, memo, lotto, stock 데이터가 있을 수 있음
메인 배포 DB 운영에 배포되어 실제로 사용 중인 데이터 pg_dump로 읽기 전용 백업 최우선 보존 대상. 덮어쓰기나 초기화 금지
AWS RDS 최종 통합 DB 초기 스키마 구성 후 staging restore와 병합 최종 전환 전 API 검증 완료 필요

권장 작업 순서

  1. RDS PostgreSQL 생성, 보안 그룹, DB명 marketpulse, 사용자 권한 확인.
  2. 로컬 DB dump 생성: schema dump, data dump, custom dump를 각각 남긴다.
  3. 메인 배포 DB dump 생성: 운영 DB는 읽기 전용으로 접근해서 dump만 수행한다.
  4. RDS 현재 상태 dump 생성: 비어 있어도 baseline으로 보관한다.
  5. RDS에 기본 schema를 먼저 반영한다. 필요한 신규 테이블 DDL도 함께 반영한다.
  6. 로컬 dump를 staging_local schema에 restore한다.
  7. 운영 dump를 staging_prod schema에 restore한다.
  8. 테이블별 row count와 primary/unique key 중복 현황을 비교한다.
  9. 충돌 정책에 따라 RDS public schema로 upsert한다.
  10. 병합 후 row count, 주요 API, 로그인, 메모, quant, lotto, stock 조회를 검증한다.
  11. 검증 완료 후 애플리케이션 datasource를 RDS로 전환한다.
  12. 전환 후 최소 1회 전체 백업을 다시 생성한다.

충돌 처리 원칙

데이터 유형 대표 테이블 충돌 기준 병합 정책
사용자/인증 users, api_token username, token type 등 unique key 운영 데이터를 우선한다. 로컬 admin 계정이 중복이면 운영 값 유지.
메모 memo, legacy investor_memo id, user, sourceType, date, market, stockCode 삭제 없이 모두 보존. 같은 맥락의 중복은 최신 updated_at 우선, 원문 충돌은 별도 검토.
종목/시장 마스터 stock_master, market daily tables code, trade_date, market 등 natural key 동일 key는 최신 updated_at 또는 더 완전한 row 우선. 누락 row는 전부 insert.
로또 lotto_result, lotto_analysis_pool, lotto_user_combo draw_no, strategy, user combo id 회차 결과는 draw_no 기준으로 동일해야 한다. 사용자 조합은 삭제 없이 보존.
Quant quant_* strategy, trade_date, run id, variant id 실험 결과는 원본 run 보존이 우선. id 충돌 가능성이 있으면 sequence 재매핑 후 insert.
스냅샷/수집 데이터 index_snapshot, news_snapshot 등 source, date, code, title/url 등 중복은 unique/natural key로 방지하고, 원본 raw JSON은 가능한 보존.

명령 템플릿

실제 host, user, db명, 파일명은 실행 전에 확정한다. 비밀번호는 명령어에 직접 쓰지 않고 환경변수나 prompt로 입력한다.

# 로컬 DB custom dump
pg_dump -h localhost -p 5432 -U won -d marketpulse -Fc -f backups/local_marketpulse_20260521.dump

# 운영 DB custom dump
pg_dump -h <prod-db-host> -p 5432 -U <prod-user> -d marketpulse -Fc -f backups/prod_marketpulse_20260521.dump

# RDS baseline dump
pg_dump -h <rds-endpoint> -p 5432 -U <rds-user> -d marketpulse -Fc -f backups/rds_baseline_20260521.dump

# staging schema 생성
psql -h <rds-endpoint> -U <rds-user> -d marketpulse -c "CREATE SCHEMA IF NOT EXISTS staging_local;"
psql -h <rds-endpoint> -U <rds-user> -d marketpulse -c "CREATE SCHEMA IF NOT EXISTS staging_prod;"

# staging restore 예시
pg_restore -h <rds-endpoint> -U <rds-user> -d marketpulse --schema=public --no-owner --no-privileges backups/local_marketpulse_20260521.dump

주의: 위 restore 예시는 스키마 매핑 방식 확정 전 템플릿이다. 실제 실행은 별도 임시 DB에 먼저 restore하거나 dump를 SQL로 변환해 schema name을 조정한 뒤 진행한다.

검증 체크리스트

  • 로컬 dump, 운영 dump, RDS baseline dump 파일 3개가 모두 존재한다.
  • 각 dump 파일의 restore 테스트가 별도 임시 DB 또는 staging schema에서 성공했다.
  • 병합 전후 전체 테이블 row count 비교표를 작성했다.
  • primary key sequence가 현재 max(id)보다 크게 재설정됐다.
  • 운영 DB에 있던 메모, 사용자, 로또 조합, quant 결과가 RDS에서 조회된다.
  • 로컬 DB에만 있던 데이터도 RDS에서 조회된다.
  • GET /api/stock/search, GET /api/memo, GET /api/lotto/latest, GET /api/quant/strategies가 정상 응답한다.
  • 관리자 로그인과 보호 API 권한 체크가 정상이다.
  • 애플리케이션 datasource 전환 후에도 같은 데이터가 조회된다.
  • 전환 완료 후 RDS 최종 dump를 남겼다.

오늘 결정해야 할 것

  • 메인 배포 DB 접속 정보와 접근 방식: 직접 DB 접속인지, SSH tunnel인지, 클라우드 콘솔 경유인지.
  • RDS를 새로 만들지, 이미 만들어진 인스턴스를 사용할지.
  • 로컬과 운영에서 같은 primary key id가 있을 때 id를 유지할지, 로컬 데이터를 재매핑할지.
  • legacy investor_memo가 남아 있다면 신규 memo 테이블로 변환해 합칠지, 별도 보관할지.
  • 전환 시점: 개발 검증만 오늘 할지, 실제 배포 datasource까지 오늘 바꿀지.
