# Bull V4 Runtime vs Backtest Gap Analysis

date: 2026-05-27
model: BULL_V4
status: root-cause found / runtime update required

## Summary

The homepage result is not reproducing the Bull V4 backtest engine yet.

Current live page data is generated by `MarketDailyPriceReplayProvider.findDailyMomentumReplayPicks()`, which is a temporary daily momentum replay. It is not the frozen Bull V4 / W4 / V3-FIN rule set from `quant-model-lab`.

This explains why the current page shows:

| source | completed trades | total return | monthly return | note |
|---|---:|---:|---:|---|
| `/api/quant/live/models/BULL_V4` runtime | 15 | -64.96% | -6.44% | daily 5-day momentum top-1 replay |
| Bull V4 research, `ap06_range040_next005` | train 38 / post 28 | train avg +3.15%, post avg +5.84% | n/a | frozen improvement candidate |
| Bull V4 research, `adaptive01` | train 51 / post 36 | train avg +2.41%, post avg +6.00% | n/a | adaptive candidate |

The runtime should therefore not be judged as Bull V4 accuracy. It is a placeholder replay with a Bull V4 label.

## Root Cause

### 1. Wrong Replay Provider

`findDailyMomentumReplayPicks()` is not Bull V4. It was useful to make the UI non-empty quickly, but it selects a different set of stocks and exits them on the same day.

Correct runtime should call a dedicated Bull V4 paper replay mapper, not the daily momentum mapper.

### 2. Signal Date and Execution Date Are Collapsed

Bull V4 separates:

```text
signal_date -> entry_check_date -> execution_date -> exit_date
```

Current runtime effectively uses:

```text
signal_date D-1 -> execution_date D -> exit_date D
```

This removes the delayed entry confirmation that made the backtest candidate stable.

### 3. Exit Logic Is Missing

Bull V4 research depends heavily on exit hierarchy:

```text
early_fail -> stop_loss -> trail -> max_hold
```

Current runtime uses same-day close as sell price, so it cannot reproduce early-fail reduction, trailing exits, or max-hold winners.

### 4. Config Drift Exists Even In Nearby SQL

`findEventDrivenCandleMtfTrendNbPicks()` is closer to Bull V4 than the current runtime, but it is not the frozen config:

| rule | frozen Bull V4 | existing SQL near-match |
|---|---:|---:|
| range20 | <= 0.40 | 0.25 to 0.55 |
| entry location | >= 0.55 | >= 0.65 |
| ret60 max | optional shadow | not applied |
| next body | >= 0.005 | execution body >= 0 |
| source | model config | hard-coded SQL |

The production version should not reuse this blindly. It should parameterize the frozen config or create a dedicated mapper.

### 5. Capital Accounting Is Not The Same

Research reports used:

```text
capital: 1,000,000,000
position_cash: 100,000,000
```

The homepage model seed is:

```text
model_seed: 100,000,000
```

That is fine for service launch, but the runtime summary must calculate:

```text
cash + open position market value + realized pnl
```

It should not compound every trade return as if each trade uses the full seed.

## Required Model Update

### Phase 1. Runtime Reproduction

Create a dedicated Bull V4 runtime replay path:

```text
BullV4ReplayProvider
  -> QuantBullV4ReplayMapper.findBullV4PaperReplayFacts(config, from, to)
```

It must emit:

```text
signal_date
entry_check_date
execution_date
exit_date
asset_code
asset_name
entry_price
exit_price
exit_reason
raw_candidate_rank
actual_entry_rank
features JSON
forward_path JSON
```

Acceptance criteria:

- Same date range and same config should produce the same trade set as the research CSV.
- Runtime report must show `source=BULL_V4_REPLAY`, not `HISTORICAL_REPLAY_DAILY_MOMENTUM`.
- Summary should show current evaluated seed, realized PnL, unrealized PnL, and cash separately.

### Phase 2. Accuracy Improvement Loop

Once runtime reproduction matches the lab, update the model through one variable family at a time:

| experiment | why |
|---|---|
| `ret60_max` 0.80 / 1.00 | reduce overextended momentum failures |
| `range20_max` 0.35 / 0.40 / 0.45 | find stability vs sample-size balance |
| `entry_next_body_min` 0.005 / 0.01 / 0.015 | control weak confirmation entries |
| `ma60_dist_max` 0.55 | avoid overheated extensions |
| market leading gate | block entries when forward market signal is weak |
| sector concentration cap | avoid clustered losses in same theme |

Each run should record:

```text
trade count
win rate
average return
median return
worst trade
MDD or worst month
early-fail rate
stop-loss rate
turnover
post-exit 1d/7d/2w/1m/6m path
```

### Phase 3. Live Paper Trading

Realtime paper mode should use two states:

```text
RAW_CANDIDATE
CONFIRMED_ENTRY
```

Reason:

- `entry_next_body_min` cannot be known on the original signal date.
- The model can watch candidates first, then enter only after confirmation.

## ReportWriter Update

The rule-based report should be fed model facts, not free text.

Minimum Bull V4 report fact schema:

```text
raw candidates
actual entry candidates
entered / rejected reasons
position changes
exit reason changes
realized pnl
unrealized pnl
expected return
risk flags
post-exit / watched-asset checkpoints
next observation points
```

This keeps the report deterministic while still making it look like a professional model report.

## Decision

Do not tune Bull V4 based on the current homepage result.

First fix the runtime so it replays the actual Bull V4 rules. After that, use the mismatch between paper/live and lab backtest as a real model-quality signal.
