## Goal

Replace the current quant backtesting-first page with a real-time simulated trading console for Market Pulse models.

The new console must show model operations, simulated positions, trade history, entry/exit plans, and automatic daily/weekly reports generated after market close.

This is not an AI/LLM report product. All model decisions and reports are produced from deterministic model output, trading logs, and rule-based templates.

## Product Direction

The old quant models and backtest tabs are no longer the primary user experience.

Existing model code should be removed during implementation, and the old work should be preserved as one HTML archive file that records what existed and why it was replaced.

The new model family is:

| Model | UI visibility | Role |
|---|---:|---|
| `INDEX_REGIME` | visible | Detect market/index regime and risk state. |
| `BULL_V4` | visible | Current bull-v4 model, upgraded into a live simulation model through a real-time execution gate. |
| `SIDEWAYS_MODEL` | visible | Sideways/range market model. |
| `BEAR_MODEL` | visible | Bear/downtrend model. Defensive by default. |
| `MASTER_MODEL` | hidden | Orchestrates which model is active, blocked, or scaled. Not directly shown as a user-selectable model. |

## Core Decisions

- Each visible model gets its own seed money of KRW 100,000,000.
- Each model manages its own position count and allocation logic.
- Real-time monitoring uses the smallest available reliable interval. MVP target is 1 minute because current data access is expected to support minute-level data at best.
- Reports are generated automatically after market close.
- Reports are generated by backend code only. No AI/LLM generation.
- Existing models are removed from active code paths. Their history is preserved in one HTML archive artifact.

## Simulation Flow

The model must separate signal generation from simulated execution.

```text
model candidate generation
-> raw candidate
-> realtime execution gate
-> simulated order
-> simulated fill
-> position
-> exit plan
-> simulated exit
-> post-decision outcome tracking
-> model learning feedback
-> daily/weekly report
```

## Post-Decision Outcome Tracking And Learning

Models must not stop caring about a stock after exit or after choosing not to enter.

The system tracks both traded assets and watched-but-not-traded assets.

Tracked asset sources:

- `TRADE_EXIT`: a stock that the model bought and later sold.
- `ENTRY_REJECTED`: a raw or filtered candidate that did not become an actual entry.
- `WATCHLIST_ONLY`: a stock the model explicitly marked as interesting even without an entry signal.
- `REENTRY_WATCH`: a previously exited stock that may deserve another entry later.

After each model decision or simulated exit, the system tracks the asset's forward path at fixed horizons:

- 1 trading day after exit
- 7 calendar days or the nearest later trading day
- 2 weeks
- 1 month
- 6 months

For each horizon, store:

- tracking source
- original decision type
- original model reason
- decision price
- exit price
- horizon close price
- max high after exit until horizon
- min low after exit until horizon
- forward return
- max missed upside after exit
- max avoided downside after exit
- whether the exit was early, late, effective, or neutral
- whether the skipped entry was correct, missed opportunity, or neutral
- whether a re-entry signal would have been useful
- deterministic checkpoint analysis text

This creates a deterministic learning loop:

```text
model decision or exit event
-> forward outcome snapshots
-> decision quality score
-> entry/exit rule feedback
-> model improvement candidate
-> explicit rule/version update
```

The learning loop must be auditable.

Rules:

- No AI/LLM learning.
- No invisible self-modifying production rule changes.
- The system can generate model improvement candidates from evidence.
- A model version changes only through an explicit recorded rule update.
- Every update must link back to the trade/outcome evidence that caused it.
- Historical model versions must remain comparable.

Example learning questions:

- Did Bull v4 exit too early before a 7-day or 1-month continuation?
- Did the stop rule correctly avoid a 1-day or 2-week drawdown?
- Did Bull v4 reject a raw candidate that later rose strongly?
- Did a watched stock fail exactly as expected, proving the filter was useful?
- Did a sideways model exit capture mean reversion but miss a later breakout?
- Did a bear model avoid losses but miss too many strong reversals?
- Which exit condition has the worst missed-upside profile?
- Which rejection reason has the highest missed-opportunity rate?

### Real-Time Fill Policy

The MVP fill policy:

- Entry and exit monitoring run during market hours at the smallest reliable interval, initially 1 minute.
- When the execution gate passes, store the observed real-time price as the simulated fill price.
- If orderbook data is available, buy fill may use ask-side price and sell fill may use bid-side price.
- If only current price is available, use current price plus a configured slippage assumption.

Every simulated fill must store:

- signal price
- observed price
- simulated fill price
- fill source: `CURRENT_PRICE`, `ORDERBOOK_BID_ASK`, `MINUTE_BAR`
- slippage assumption
- model reason
- data timestamp

### Bull v4 Live Upgrade

Bull v4 remains the current alpha/source model.

For live simulation, Bull v4 becomes:

```text
BULL_V4 signal model + realtime execution gate
```

Bull v4 is responsible for:

- raw candidates
- entry eligibility
- expected return
- exit rule
- risk flags

The realtime execution gate is responsible for:

- checking latest current/minute/orderbook data
- creating simulated fills
- updating positions
- triggering exits

## Report Generation

Reports are deterministic and generated without AI.

### Model Fact Output

Each model writes structured facts after each run/day:

- raw candidate count and list
- filtered candidate count and list
- actual entry list
- rejected candidate reasons
- open positions
- exit plans
- realized trades
- unrealized P/L
- total return
- monthly return
- warnings
- next-session watch list
- post-decision checkpoint updates
- learning feedback candidates

### Rule-Based Report Writer

`RuleBasedReportWriter` converts structured facts into daily/weekly reports using code templates.

Rules:

- same input produces same report
- report text cannot invent numbers, tickers, or reasons
- all numbers come from stored logs/facts
- missing data is written as missing data, not inferred
- each newly completed 1-day, 7-day, 2-week, 1-month, or 6-month checkpoint is summarized in the next daily/weekly report
- daily reports run after market close
- weekly reports run after the last market session of the week

## Acceptance Criteria

- AC-1: `/quant` shows a list of four visible models: index, bull, sideways, bear.
- AC-2: `MASTER_MODEL` is not directly visible as a selectable model.
- AC-3: Each visible model has independent KRW 100,000,000 seed money.
- AC-4: Model detail exposes current positions, raw candidates, actual entries, trade history, exit plans, and expected return.
- AC-5: Simulated fills store signal price, observed price, fill price, timestamp, source, and slippage assumption.
- AC-6: Live monitoring runs at the smallest reliable available interval, MVP 1 minute.
- AC-7: Daily reports are generated automatically after market close without AI/LLM.
- AC-8: Weekly reports are generated automatically after the final market session of the week without AI/LLM.
- AC-9: Reports are viewable in the homepage report tab with list and detail views.
- AC-10: Reports are deterministic from stored facts/logs and do not invent values.
- AC-11: After exit, each closed trade is tracked at 1 trading day, 7 days, 2 weeks, 1 month, and 6 months where data is available.
- AC-12: Watched-but-not-traded assets are also tracked at the same horizons when a model marks them as raw, rejected, watchlist, or re-entry watch.
- AC-13: Outcome tracking records missed upside, avoided downside, forward return, decision quality, and exit/rejection quality classification.
- AC-14: Newly completed outcome checkpoints appear in daily/weekly reports with deterministic analysis text.
- AC-15: Models generate deterministic learning feedback from outcome checkpoints without AI/LLM.
- AC-16: Production model rule/version changes require an explicit recorded update and are not silently self-modified.
- AC-17: Old quant models are removed from active code paths.
- AC-18: Old model history is preserved in a single HTML archive.
- AC-19: Existing non-quant site pages remain unaffected.
- AC-20: Backend compile, frontend build, and focused quant tests pass.

## Open Implementation Notes

- Market-hour and holiday handling should use KRX trading calendar if already available; otherwise define a conservative service boundary to add it.
- If current KIS data limits prevent true 1-minute polling for all candidates, record `DATA_DELAYED` and degrade to the best available interval without hiding the limitation.
- Bear/sideways model rules may start as shells if not yet defined, but the model list and report contract should be ready from the first implementation.
