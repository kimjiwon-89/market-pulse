# Production Database Redesign Direction

Prod owns the canonical DB schema. Lab proposes data contracts and migrations; prod accepts, implements, tests, stages, and releases.

## Design Goals

- Preserve already collected market data.
- Support many quant, lottery, pension lottery, and tarot model versions.
- Separate research outputs from production-approved serving data.
- Make account/auth extensible before real users arrive.
- Make indexes, unique keys, and sequences explicit.
- Keep every table grain clear.

## Sequence And ID Policy

Use PostgreSQL identity columns for new numeric IDs:

```sql
id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
```

Rules:

- Do not create unnamed/manual sequences unless legacy migration requires it.
- Natural unique keys must still exist even when table has surrogate `id`.
- High-volume fact tables should prefer natural/composite uniqueness for idempotent upsert.

## Index Policy

Every migration must explicitly define indexes for expected query paths.

Required patterns:

- Date-range lookup: `trade_date`, `draw_no`, `run_at`, or equivalent time key.
- Entity lookup: `stock_code`, `market_code`, `model_code`, `user_id`.
- Version lookup: `model_code`, `model_version`, `status`.
- Latest snapshot lookup: descending date/run indexes where needed.
- Unique idempotency keys for ingestion/backfill jobs.

## Target Table Domains

### Reference And Market Data

- `market`
- `stock`
- `stock_listing_history`
- `index_master`
- `index_daily_price`
- `stock_daily_price`
- `stock_chart_bar`
- `market_snapshot`
- `news_snapshot`

Core grain:

- one row per market/index/stock/date/bar interval, depending on table

### Investor Flow

- `investor_type`
- `investor_flow_daily`
- `investor_flow_ranking_snapshot`
- `investor_flow_collection_run`

Core grain:

- one row per trade date, market, stock, investor type

Indexes:

- `(trade_date, market_code, investor_type)`
- `(stock_code, trade_date)`
- `(trade_date, investor_type, net_amount DESC)`

### Quant Model Serving

- `model_family`
- `model_version`
- `model_run`
- `model_input_dataset`
- `quant_feature_snapshot`
- `quant_signal`
- `quant_portfolio_target`
- `quant_backtest_result`
- `quant_trade_log`
- `model_metric`
- `model_promotion`

Core grain:

- model metadata: one row per model/version
- feature/signal: one row per model version, signal date, stock
- portfolio target: one row per model run, rebalance date, stock
- metrics: one row per model run and metric key

Required separation:

- `model_version`: accepted model identity
- `model_run`: execution instance
- `model_input_dataset`: data snapshot used for run
- app release version is not model version

### Lottery And Pension Lottery

- `lottery_game`
- `lottery_draw`
- `lottery_draw_number`
- `lottery_model_version`
- `lottery_model_run`
- `lottery_prediction`
- `lottery_prediction_number`
- `lottery_metric`

Core grain:

- game supports `lotto` and `pension_lottery`
- one draw table shape with game-specific number tables
- model prediction tied to game, draw target, model version, and run

### Tarot

- `tarot_deck`
- `tarot_card`
- `tarot_spread`
- `tarot_prompt_version`
- `tarot_reading`
- `tarot_reading_card`

Core grain:

- prompt/model versions are explicit
- user reading content is user-sensitive and retention-limited

### Account/Auth

- `account`
- `auth_identity`
- `auth_credential`
- `auth_session`
- `account_role`
- `account_role_assignment`
- `account_audit_event`
- `consent_record`

Rules:

- `account` is the stable user entity.
- `auth_identity` maps provider identity: local, Google, Kakao, Naver, admin, service.
- `auth_credential` stores local password hash metadata only, never raw passwords.
- `auth_session` stores refresh/session lifecycle.
- audit events record security-relevant changes.

## Migration Request Acceptance Checklist

Every accepted migration must include:

- purpose
- owner
- table grain
- PK/FK
- unique constraints
- indexes
- sequence/identity behavior
- backfill plan
- rollback expectation
- validation query
- data sensitivity note
